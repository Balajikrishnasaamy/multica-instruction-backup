3. Must have

Things that, if left undone, will make the first real runs fail, mislead you, or put something at risk.

M1. Run one small real issue through the whole loop, supervised

Why: it is the only way to find out whether the instructions are followed in practice: single-mention rule, git -C path rule, loop breaker, HANDOFF format, Reviewer's 20-minute deploy call, the DEPLOY block, the attached HTML report, TEST-OK, MR link. Today the design is proven in parts only.

Effort: small. Pick a trivial circuit change, CirDoc-P with Worker-1, and watch the run. Feed every surprise to the Curator.

DONE 2026-10-28 M2. Fix qntrlcore checkout (3 branch pairs that differed only in letter case)

What was wrong: the qntrlcore remote had three branch pairs whose names differed only in case (SDP_DUMMY/sdp_dummy, HACKSAW_ISSUE_FIX/hacksaw_issue_fix, SECURITY_BUG_FIX/security_bug_fix). Your manual clone worked because git clone stores refs in one packed file; the daemon's second fetch writes one file per branch, so each pair collided on this case-insensitive APFS volume, git exited 1, and the daemon dropped the repo cache.

What fixed it: you deleted one branch of each pair on the remote. I re-ran the daemon's clone and backfill fetch (exit 0, no collisions), then restarted the daemon, which re-cloned qntrlcore with all 3,612 branches.

Still open: one real multica repo checkout of qntrlcore by an agent. If anyone recreates a branch that differs only in case, this breaks again; circuit and qntrlworker have no such pairs.

M3. Check that each runtime may run what its agents need

Why: the Curator was blocked on the Claude runtime ("requires approval") until moved to Copilot. Cursor's config allows only ls. A worker that cannot run git, python3 or run_test.sh will stall or loop. Make a small per-runtime test (git, run_test.sh, multica, lessons.py) and set the allow-lists or the runtime choice before assigning roles.

Effort: small. Needed before Worker-1 runs on Cursor.

M4. Prove the real deploy and the rollback once, deliberately

Why: restart, health check and automatic rollback are the riskiest code and have never touched the real server. Do one deploy of a harmless commit while you watch, then one deploy of a commit that breaks startup, and confirm the old jars come back and the server returns. Do the second one on a copy of the build if possible.

Effort: small, 30 minutes, you present.

M5. Stop treating a down dependency as a bad build

Why: the deploy rolls back on any [ FAILED ] service. Your Oct 26 log shows ReactorWorkerService failing once with no recorded cause. If MySQL or Cassandra is down, every deploy would roll back and blame the worker. Add a preflight to deploy_dev.sh that checks MySQL (3306) and Cassandra (9042) and exits with "environment down" before touching any jar.

Effort: small.

M6. Serialize use of the dev server across issues

Why: there is one dev server. Deploying issue B replaces issue A's classes while you may be testing A, and your TEST-OK on A would then be on the wrong build. Today this is only a sentence in the instructions. Add a reservation (issue id, sha, time) that the deploy script checks and Classify & Route reads, so the second issue waits.

Effort: medium. Matters as soon as CirDoc-P and CirDoc-O run at the same time.

M7. Deploy config changes, or refuse to call the build "deployed"

Why: the script ships Java classes only. Many Circuit fixes are config or security XML (your own working tree has changes to security-rule.xml, functional.conf, integration.conf), and those are exactly the high-risk files. A TEST-OK on such a build tests something that is not running. Copy product_package/conf files from the commit to the build, or make Reviewer report partially_deployed and block the gate until you confirm.

Effort: medium.

M8. Protect secrets and shrink what agents can reach

Why: agents run with your full rights, and qntrl_run.sh keeps KMS, Transmail and client tokens in plain text and appends them to a config file on every run. Rotate the Multica token that was printed, move local secrets to a chmod 600 env file, and run agents from a dedicated macOS user or at least outside the home directory that holds ~/Build. The backup tooling already skips qntrl_run.sh.

Effort: small for the rotation and env file, medium for a separate user.

M9. Put the backup folder under version control

Why: multica-instruction-backup is now the source of truth for all agent instructions, tools and lessons, and it exists only on this laptop. Make it a git repo with a private remote and commit after every apply or approved lesson.

Effort: small.

M10. Confirm the MR step against GitLab

Why: the push options and the link capture from the push output were only tested on a local server. If GitLab prints the link differently, or the options are rejected, the last step of every issue fails. Check with a throwaway branch and a draft MR, and confirm that cleanup of the review branch works.

Effort: small. Can be part of M1.

4. Good to have

Improvements that make the setup cheaper, easier to trust or easier to run. None blocks a first run.

G1. Notifications for the moments that need you

Why: the loop waits on you at TEST-OK, ESCALATE, blocked and failed deploys. Today you must watch Multica. A Cliq or Slack message at those points is step 8 of your own flow diagram and shortens every cycle.

G2. Replay tests for the instructions

Why: every instruction change is currently tested by waiting for a real issue. A few mock issues (a clean fix, a failing test, a failed deploy, a plan conflict) that run against a scratch repo would catch regressions like the mention-in-ROUTING bug before they cost real runs.

G3. Enforce "only Reviewer deploys" in tooling

Why: at the moment it is a rule agents are told. A signed token the Reviewer run receives, or a check on the calling workdir, would stop a confused worker from restarting the shared server.

G4. Choose one model per role and retire weak combinations

Why: Worker-O on glm-5.3-flash looped 476 times, while the Curator on a stronger model followed its instructions precisely. Decide models by evidence after the first real runs, and record them in the backup so they are not lost.

G5. Extend tests beyond circuit, and fix the two broken classes

Why: qntrlworker and qntrlcore have no automated tests, so for them the only test is yours. EntityUtilTest and CriteriaQueryParserTest do not compile on the clean branch (lesson W-001 works around it). Step 7 of your diagram, suites plus integration plus k6, does not exist yet.

G6. Cost and runtime budgets per issue

Why: one stuck run used 20 million cached tokens before it was cancelled. multica issue usage exists. A daily report, and an automatic cancel above a tool-call or time threshold, caps the damage of a loop the model fails to break itself.

G7. Keep the machine awake and the daemon supervised

Why: if the laptop sleeps or the daemon stops, nothing runs and an in-flight deploy can be left half-done. Use caffeinate or a launchd service, and an alert when the daemon heartbeat stops.

G8. A status page

Why: one HTML page showing open issues by stage, the last deploy (deploy/last.json), the latest test reports and pending lesson proposals would replace several Multica tabs and the log reading done today.

G9. Housekeeping

Why: there are about 70 old task workdirs and a growing set of test reports and backups. Prune on a schedule. Also note that jar uf cannot remove classes, and 5 deploy backups is a short horizon for a build that qntrl_run.sh reinit can wipe.

G10. Curator sweeps and lesson review

Why: the Curator only looks at issues Classify & Route flags. A weekly sweep of all finished issues would catch problems nobody flagged, and a review of lessons older than a month would retire the ones that no longer apply. Lessons cost context on every run, so the 12-per-section cap should be watched.

G11. Separate dev servers for CirDoc-P and CirDoc-O

Why: removes M6 for good and lets two squads run in parallel. It needs a second build directory and different ports, so it is the largest item on this list and only worth it if you run both squads daily.

G12. Record which build the dev server is running

Why: after several patched deploys the server differs from any official build. A small file or endpoint listing the patched jars and SHAs would answer "what am I testing?" without reading history.
